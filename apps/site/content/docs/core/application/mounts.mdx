The **Mounts** tab has two views: 

- **Volumes** for persistent data, 
- and **File Mounts** for configuration content Belune manages and bind-mounts read-only into the container. 

Both survive redeploys and restarts.

## Volume Mounts

<Screenshot name="app-volume-mounts" alt="An application's volume mounts, mapping a named volume to a container path." />

**Add Volume** takes a name and an absolute mount path inside the container, e.g. `/data`. A volume attaches when the container is created, so a [reload](/docs/core/application/deployments) is enough to apply a newly-added one with no rebuild needed, and the application's status badge flags when a reload is outstanding. 

Removing a volume detaches it on the next deploy. By default the underlying data is kept (so recreating a volume with the same name reattaches it); check **Also permanently delete the stored data** to destroy it immediately and irreversibly.

<Callout type="warn" title="About the mount path">
The mount path should not be a system path like `/`, `/tmp`, or `/etc`.
</Callout>

### Adopting Existing Volumes

An administrator can choose **Adopt Existing Volume** to attach data already stored in a Docker named volume on this server. Enter its exact Docker volume name, a mount name for this application, and the absolute path inside the container. Reload the application to attach it; Belune does not copy the data or create a replacement if the named volume is missing.

Remove the old external container first, while keeping its volume. A volume already attached to another application or managed by Belune cannot be adopted. One adopted volume can belong to only one application at a time.

For example, a Postgres container previously run by raw Docker Compose can move into Belune as an **image application**, using its existing image and volume mount. This does not turn it into a managed database. Adoption into managed databases, host bind mounts, shared volumes, external network joins, and remote servers are outside this feature.

Adopted volumes are marked **Adopted**. Removing their mount, deleting the application, or deleting its project leaves their data behind and protected from manual and scheduled cleanup. An unattached adopted volume can be adopted again. After detaching, reload the old application before adopting its volume elsewhere: a running container can still hold the old mount until it is replaced. In **Docker → Volumes**, unattached names remain visible as **Adopted, no application**. They are retained deliberately; removing the Docker volume is a host-side operation with `docker volume rm <name>`. Belune has no Release action. Protection remains for the name if the volume is later recreated.

Backups can read an adopted volume. Restoring into one is disabled to preserve its existing data. Deleting an application still destroys that application's volume backup archives, including remote copies, even though its adopted volume itself is retained.

### Backing Up Volumes

The **Backups** section below **Volumes** is a list of schedules that snapshot a volume to one of the project's [backup destinations](/docs/core/project/backup-destinations) on a cron schedule, or on demand via **Back up now**. A volume can back up to more than one destination, but needs both a volume and at least one project destination configured first. 

Each schedule tracks its own run history, browsable from **Manage Histories**. Deleting a schedule also deletes the backups it produced from that destination.

## File Mounts

<Screenshot name="app-file-mounts" alt="File and config mounts managed in Belune and bind-mounted into the container." />

**Add File** takes an absolute file path, the file's content, and an optional file mode (default `0644`). 

For example, in an `nginx` application you'll want to configure `nginx.conf` to make sure it works for your setup: fill in the path as `/etc/nginx/nginx.conf`, and the content you'd like to configure.

<Callout type="warn" title="About the file path">
The parent directory of the file path must exist in the image.
</Callout>

The content you type is written to a managed host file and bind-mounted read-only into the container on the next deploy or reload.

<Callout type="warn" title="About the file content">
The application can't write to the file, as the file content is managed by Belune.
</Callout>

### Secrets

Marking a file mount **Secret** masks its content in the UI. The edit dialog shows the content hidden by default, with a **Reveal current content** step required before you can see or edit it in place. 

This mirrors how secret environment variables and other credentials are handled: nothing sensitive round-trips to the browser unless you deliberately ask for it.

## Lifecycle

Neither kind of mount needs a rebuild to take effect: both are attached when the container is (re)created, so a reload picks up any mount change. 

Editing a file mount's content, in particular, is exactly the kind of change reload exists for: the image doesn't change, only what's bind-mounted into it.
