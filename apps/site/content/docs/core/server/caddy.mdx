Belune puts every domain behind Caddy and configures it through Caddy's admin API. Which Caddy you run decides which optional features are available. Nothing else changes.

## The Default Image

Belune's stack runs `ghcr.io/belune-hq/belune-caddy:2`: upstream Caddy plus seven optional modules (rate limiting, the Cloudflare, Route 53 and DigitalOcean DNS providers, a WAF, CrowdSec, and layer 4 proxying). Rate limiting, the WAF and CrowdSec each have controls in the dashboard; a module without a feature yet ships ahead of it, so that turning it on later doesn't mean replacing the proxy again.

You don't have to use it. Stock upstream `caddy:2-alpine` is a supported setup, not a degraded one: every core function (routing, automatic and custom TLS, basic auth, headers, IP allowlists, redirects, path routing) works the same. Set `BELUNE_CADDY_IMAGE` in `.env` to switch, and run `update.sh` (or `docker compose up -d`) to recreate the proxy. See the [configuration reference](https://github.com/belune-hq/belune/blob/main/docs/configuration.md) for the variable.

<Callout type="info">
Recreating the Caddy container, which is also what upgrading to 0.2.0 does, makes your domains briefly unreachable while the new container starts.
</Callout>

## Features That Need a Module

Belune asks the running Caddy which modules it has (`caddy list-modules`, run inside its container) and checks again whenever the container is recreated. It never guesses from the image name.

| Feature | Module it needs |
|---|---|
| Rate Limit | `http.handlers.rate_limit` |
| WAF | `http.handlers.waf` |
| CrowdSec | `http.handlers.crowdsec` |

When the module is missing the feature is **not configured**, never an error:

- You can't enable it, and the type is shown disabled in the domain's route features with the reason.
- A feature you saved earlier stays stored but shows as **Not active**, and the domain keeps serving without it. Switch back to an image with the module and it applies on the next reconcile, with no re-entry.
- If Belune can't reach Caddy to ask (for instance while it restarts), it makes no claim either way: you can still save the feature, and a domain is only ever served with a feature the running Caddy is known to have.

## Bring Your Own Caddy

Belune manages Caddy entirely through its admin API; it never writes a Caddyfile. A Caddy that works with Belune needs:

1. **The admin API reachable from Belune**, at `CADDY_ADMIN_URL` (default `http://localhost:2019`; the bundled stack sets `http://caddy:2019`). Keep it off public interfaces: it can reconfigure everything.
2. **A single HTTP server named `srv0`.** Every route is written to `srv0` by name. A Caddyfile with one `:80` site block produces it; a `:80, :443` block would split into `srv0` and `srv1` and strand the routes on the wrong one. Belune sets the listeners to `:80` and `:443`, the automatic-HTTPS policy and the TLS connection policy itself.
3. **A Docker container Belune can find.** It looks for the label `belune-system=caddy`, or the name in `CADDY_CONTAINER_NAME` (default `infra-caddy-1`), which is the way to name one that doesn't carry the label. Belune runs `caddy list-modules` inside it and joins it to each project's Docker network so it can reach your apps. A Caddy outside Docker can still be routed to, but you take over the networking, and because Belune can't ask it for its modules, module-backed features are left off.
4. **The standard handlers Belune emits**, all part of upstream Caddy: `reverse_proxy`, `rewrite`, `static_response`, `subroute`, `headers` and `authentication` (HTTP basic), with the host, path and remote IP matchers; the `load_pem` certificate loader; and the file log writer with the filter encoder. Any upstream build has them.
5. **The access log volume.** Belune writes a JSON access log to `/var/log/caddy/access.log` inside the Caddy container and reads it from its own, so both mount the same volume there. The file holds request entries only, and the secrets that travel in request URLs (a deploy hook token, and the `?token=` of a password-reset or invitation link) are replaced with `[REDACTED]` before they are written. Caddy's own container log, which the Maintenance panel shows, carries diagnostics such as certificate errors but no request lines; requests are in each application's request log.

Belune treats its own routes as the source of truth and re-asserts them every 30 seconds, so a host route you add to Caddy by hand will be removed. Optional modules are a bonus, never a requirement.

## The Proxy Page

Admins get a Proxy page in the sidebar, with a tab each for Caddy, CrowdSec and the WAF. The Caddy tab shows what Belune can tell about the proxy itself: which container it is and how that container was found, whether the admin API answers, the version and image, the loaded modules, whether the request log is being read, how much traffic Caddy is proxying to apps and how fast, and how the live routes compare with the database.

Every line separates "could not be determined" from "not there". If Belune cannot list Caddy's modules because the proxy is restarting, the page says the modules are unknown rather than that they are missing. When Caddy runs outside Docker there is no container to inspect, and the page says so instead of reporting an error. The CrowdSec and WAF tabs are described below.

The traffic figures come from Caddy's own metrics, so they cover requests that reached an app and not redirects or the dashboard itself. They need `servers { metrics }` in the Caddyfile, which Belune's stack already sets. A Caddy you run yourself needs the same.

Apart from the Trusted Proxies card described below, the page is read-only. Belune owns the route table and rewrites anything it does not recognise within thirty seconds, so Caddy's configuration cannot be edited here. The running configuration can be viewed, with private keys and password hashes removed on the server. Reconcile Routes stays on the Server page, beside the other maintenance actions.

## Behind a CDN or Load Balancer

If a CDN or load balancer sits in front of Caddy, every request reaches Caddy from that service's address, so Belune would take your visitors for the CDN. The Trusted Proxies card on the Caddy tab tells Caddy which peers are proxies. For a request from one of them, Caddy reads the visitor's address from the `X-Forwarded-For` header the proxy sent. It is empty by default, and it should stay empty if visitors connect straight to your server.

To set it, open **Proxy**, then the **Caddy** tab, paste the proxy's addresses or ranges (one per line), and **Save**. It applies within seconds, and saving an empty list stops trusting any proxy. **Add Cloudflare Ranges** fills in Cloudflare's published list, which is a snapshot: the card shows the date it was copied and links to the page to check it against. Belune does not keep it current. A new Cloudflare range missing from your list does not let anyone forge an address; visitors arriving through it are simply shown as that Cloudflare address until you add it.

What to know before listing a proxy:

- **A listed address can claim to be anyone.** Whatever a trusted proxy says the visitor's address is, Belune believes. Only list a CDN you use or a network you control.
- **Never list a range your own apps run in.** Caddy shares a Docker network with every app, so a container on one can connect to it. If its network is listed, that container can claim any address, and with automatic bans on, have that address banned. The card names any listed range that overlaps a network Caddy is attached to. If it says it could not check, Belune could not list its Docker networks at that moment, and the answer is unknown, not "no overlap".
- **A visitor cannot choose their own address.** Caddy reads `X-Forwarded-For` from the right, skipping the proxies you listed, so a header the visitor adds in front of the proxy's own entry is ignored. This is always on and has no setting.
- **Rate limits and IP allowlists follow the visitor.** A domain's rate limit counts each visitor separately, and its IP allowlist matches the visitor's address, not the proxy's. With no proxy listed they use the connecting address, as before, and a forged `X-Forwarded-For` cannot get past an allowlist.
- **CrowdSec is unchanged.** The advice under CrowdSec about running behind a CDN still applies.

## The WAF

The WAF tab turns on a web application firewall in front of your applications, and it **only detects**. Nothing is blocked. With it on, requests to your applications are checked against the [OWASP Core Rule Set](https://coreruleset.org/) by the `http.handlers.waf` module (Coraza) that the Belune Caddy image carries, and each rule that matches is recorded so you can see what would have been blocked. It is off until you turn it on, and the switch covers every application at once.

What to know before turning it on:

- **It inspects your applications, not the dashboard.** The dashboard's own API takes commands, scripts and credentials as ordinary input, which a generic rule set reads as attacks.
- **Large uploads are never touched.** Request bodies over 128 KiB, or of unknown length, are not inspected, so a payload inside one goes unseen. The module's defaults were measured to stall and truncate bodies over about 1 MiB even in detection-only mode, so this is what keeps uploads working. URLs, headers, query strings and smaller bodies are inspected.
- **The matched text is never stored.** Neither is the request body, and of the request's headers exactly two are kept by name: `Content-Type` and `User-Agent`. An allowlist rather than a denylist, because keeping every header would mean keeping whatever an application invents, including its own credentials. What a detection keeps of its own is the rule, its severity and class, the client address, the host, and the name of the field the rule matched in — the name only, never what was found there. The URL, method, status and those two headers are shown beside it from the request log, so a detection whose request log has been swept shows the rule without the request.
- **False positives are shared.** One noisy application fills the same detection log as the rest. That is tolerable while nothing is blocked, and it is the reason blocking, when it arrives, will be per application.

The table groups detections by the client that caused them, because a single scanner writes thousands of them and a flat list of those says only that something is happening. One row per client gives its hits, the requests they came from, the URLs they were aimed at and how many distinct rules matched — a request can trip a dozen rules, so hits normally outnumber requests. A **Would block** flag means at least one of those requests passed the anomaly-score threshold, which is the difference that matters: a client with hundreds of hits and no flag is usually one application sending a content type the rule set dislikes. Expanding a row lists that client's detections rule by rule, each timed to the second, with the method, status and host of the request each matched, and the rule's own class beside it. That class is the rule set's, not Belune's: an injection or file-inclusion class (`sqli`, `xss`, `rce`, and the rest) means a payload matched an attack signature, while `protocol` means only that the request was not formed the way policy expects. Severity cannot carry that distinction, because 920420 reports `critical` exactly as a SQL injection match does, and it is the same distinction CrowdSec's autoban is built on. A rule that declares no class shows a dash; the anomaly-score summary is the one you will see it on, since it is a verdict on the whole request rather than one signature.

The eye beside a rule match opens everything Belune kept about it: when it was recorded, the client, the host, the field the rule matched in, the method and status, the whole URL including its query, and the two request headers that are stored.

**Matched in** is the single most useful line for telling your own traffic from someone else's. It names the request variable the rule fired on — `REQUEST_COOKIES:session`, `ARGS:q`, `REQUEST_HEADERS:User-Agent` — and never what was found in it, because the matched text is the payload and is not stored. A rule that judges the request as a whole, such as the anomaly-score summary, reports no field and says so. Treat the name as a pointer rather than as proof: it is read from the rule's own output, which the request can influence.

**The whole URL, query and all, is shown only here**, and it is the reason the panel exists: a query string carrying an injection attempt runs past any column width, and it is the part you read to judge the detection, so the table shows what can be taken in at a glance and the panel shows the request whole. The count of distinct URLs stays on the client row above. The content type is kept for the same reason: rule 920420 ("Request content type is not allowed by policy") fires on a plain `text/plain` POST, and the content type is the whole of the difference between that and an attack. The two headers are an allowlist, so the panel names the ones it keeps rather than letting their absence read as evidence about the request.

The period above the summary scopes the table as well, so it is also how you ask what happened recently. Clients are listed loudest first, and the list is capped rather than paged — under a broad scan it says when more clients matched than it showed, and a narrower period or a client address filter is the way through. A client whose request logs have already been swept shows no URL count, which the column says in words rather than as a bare zero.

Detections are kept for seven days and at most 200,000 are kept, whichever limit is reached first, so an attack cannot fill the disk. The retention is a setting on the Server page. If events are lost, because Belune was too busy to record them or a log line did not have the expected format, the tab says so rather than showing a count that quietly reads low.

The three states of "does this Caddy have the module" stay separate here too. If Belune cannot list Caddy's modules, the tab says it cannot tell yet and still lets you turn the switch on, which then takes effect once Belune can ask. Only a Caddy that is known to lack the module is refused. With stock Caddy the WAF is simply not available, and everything else keeps working.

The rule matches also appear in the proxy's log on the Server page. Because they carry the matched text, that view shows each one as a summary, the rule, the client and the host, with the payload and URL withheld. The unredacted lines stay in Docker's own log for the proxy container on the host.

## CrowdSec

The CrowdSec tab bans addresses from your applications. A ban is a decision held by a CrowdSec local API, and the `http.handlers.crowdsec` module in the Belune Caddy image asks it about every request's address and answers a banned one with a 403, on every application hostname, within about five seconds of the ban being placed or lifted. It is off until you turn it on, and the switch covers every application at once.

### What Runs

Belune's stack gains one service, `crowdsec`, running only CrowdSec's local API. Its log-parsing agent and its link to CrowdSec's central API are both switched off, so **nothing is banned that you or your own policy did not ban, and nothing leaves your server**: no community blocklist (which would ban addresses behind shared NAT and CDNs) and no signals sent out. It idles at about 70 MB with a 256 MB ceiling, and its image is about 170 MB to pull. It always runs, because a dashboard cannot start a compose service; the switch decides whether Caddy consults it.

Belune drives it by running `cscli` inside that container, the same way it runs `caddy list-modules` in Caddy's. The only secret Belune holds is the bouncer's key, which can read the ban list and nothing else. CrowdSec generates it, Belune stores it encrypted and hands it to Caddy, and it never appears on a command line or in a response.

A release that adds this service changes the compose file, so updating to it restarts the stack briefly, and a host that has not run the update shows the tab as **Local API down**.

### What Is Never Banned

The ban list is the one place in Belune where a mistake locks someone out, so the ways to get it wrong are closed off.

- **The dashboard is not behind the bouncer.** It covers your application hostnames only, so a ban can always be lifted from the table on this page.
- **An admin's address is protected by an allowlist entry, for 30 days from the last login.** Turning CrowdSec on puts the address you are connected from on an allowlist, and so does every admin login. CrowdSec refuses to ban an allowlisted address, or a range that contains one, and adding an address to the allowlist **lifts a ban already on it**, so logging in undoes a ban that caught you. Belune never overrides the allowlist. A public address is safe only while its entry stands, and the tab says whether yours is on the list. Private and loopback addresses can never be banned, so they are never added.
- **Private, loopback and reserved addresses are refused.** In a Docker deployment the address Caddy sees can be a gateway or proxy that every visitor shares, and banning it bans them all. A range must be no wider than /16 (IPv4) or /48 (IPv6).
- **Every ban expires**, between one minute and 365 days. There is no permanent ban.
- **Lifting a ban never needs the feature switched on**, and neither does leaving the allowlist.

Every ban, lift and allowlist change is in the audit log with who made it.

### Automatic Bans

Off by default, and separate from the switch above. With it on, Belune bans an address that trips the [WAF](#the-waf)'s attack rules in enough separate requests within a window, by default 10 requests in 10 minutes, for one hour, with at most 25 automatic bans in force at once. It needs the WAF turned on, since the WAF is what produces the detections.

What counts is chosen so that it cannot be set off by ordinary traffic:

- **Distinct requests, not rule matches.** One request trips many rules, and a single crafted request must not be able to ban an address.
- **Attack categories only**: SQL injection, cross-site scripting, remote code execution, file inclusion, PHP and Java injection, and optionally server-side request forgery and template injection. Protocol and request-format rules never lead to a ban. They share the critical severity of real attacks, and one of them fired on ordinary `text/plain` POSTs, so severity could not be the test.
- **A lifted ban stays lifted.** An address you unban from this page is not banned again for the length of the window, however many detections it already has. A ban lifted with `cscli` on the host is not recorded, so allowlist the address as well (the commands are below).
- **A cap, and it says so.** When the cap is reached further addresses are left alone and the tab reports it: something is tripping rules at a rate worth looking at.

A visitor whose form contains SQL or script text can still trip attack rules, which is why this asks for confirmation the first time and why every ban expires.

### When Something Is Wrong

Caddy **fails open** by design: a bouncer that cannot do its job lets everyone through. That keeps a CrowdSec problem from taking your sites down, and it means a ban can stop being enforced without anything looking wrong, so the tab reports whether enforcement is live and not just configured.

- **The local API is down.** Caddy keeps enforcing the bans it already holds and does not learn of new or lifted ones. If Caddy's configuration changes while the local API is down, which any deploy or domain change does, it starts again with an empty list and enforces nothing until the local API answers.
- **The bouncer has stopped fetching the ban list**, most often because its entry was changed by hand in the local API. The tab shows **Not enforcing** and offers to rotate the key.
- **Behind a CDN or load balancer** Caddy sees that service's address and not your visitors', so a ban would block everyone using it. Do not use CrowdSec there.
- A Caddy that is known to lack the module is refused. If Belune cannot list Caddy's modules, the tab says it cannot tell yet and still saves the switch, as the WAF does.

### If a Ban Locks You Out

You should never need this, since the dashboard is outside the bouncer. If you cannot reach the dashboard at all, connect to the server over SSH. **The host shell in the dashboard will not help**: it sits behind the same login you cannot reach.

```bash
cd /opt/belune
docker compose exec crowdsec cscli decisions delete --all
```

That lifts every ban, and Caddy picks it up within seconds. To lift one address, use `--ip 203.0.113.9`, or `--range 203.0.113.0/24` for a range. To switch CrowdSec off without the dashboard:

```bash
docker compose exec postgres psql -U belune -d belune -c "UPDATE crowdsec_config SET enabled = false"
```

Belune removes the bouncer from Caddy within 30 seconds.
