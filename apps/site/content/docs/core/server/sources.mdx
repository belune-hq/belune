The **Sources** page brings together personal git connections, admin-managed provider apps, and install-wide registry credentials. Non-admins see Connections; administrators also see Providers and Registries.

<Screenshot

/>

## Providers Vs. Connections

- A **Provider** is an app registration — a GitHub App, or an OAuth client ID/secret pair, that makes connecting possible at all.
- A **Connection** is one actual linked account, authenticated through one of those providers.

<Callout type="info">
  Registering providers is an admin-only capability, since a provider app is a
  platform-wide credential, not a personal one.
</Callout>

## Supported Providers

<Screenshot name="git-provider-add" alt="The add Git provider form dialog." />

Four providers are supported, added from **Providers → Add provider**:

- **GitHub** — cloud-hosted, and the only provider with the richer GitHub App flow (see below).
- **GitLab** — cloud-hosted by default, or self-hosted with an optional base URL.
- **Bitbucket** — cloud-hosted.
- **Gitea** — self-hosted only; a base URL is required.

### Register A GitHub App

GitHub gets a dedicated flow instead of manual OAuth:

1. On the create provider dialog, pick **GitHub** provider
2. On Visibility field choose **Private** (only your admin account can connect through it) or **Public** (any team member can connect their own account)
3. On the **Organization** field, optionally scope the provider to an organization
4. Click **Create GitHub App** button. You're redirected to GitHub to create and install the App from a manifest
5. After redirect back, the provider is configured automatically.

### Register An OAuth Provider

GitLab, Bitbucket, and Gitea are registered as standard OAuth apps:

1. On the create provider dialog, pick the specified provider
2. On the Visibility field set the provider visibility (Private/Public, same meaning as above)
3. On the Base URL field, enter base URL if self-hosted (required for Gitea)
4. Go to the provider settings page, register Belune's **callback URL** shown in the dialog (`/api/git/integrations/callback`).
   - GitLab: On the group page, go to **Settings** → **Applications**
   - Bitbucket: Go to **Workspace settings** → **Apps and features** → **OAuth clients**
   - Gitea: Go to **Settings** → **Applications** → **Create a new OAuth2 Application**
5. Enter the **Client ID** and **Client secret** from an OAuth app you create on that provider.

<Callout type="info">
  The client secret is stored encrypted and is never shown again after saving.
</Callout>

## Connect Your Account

<Screenshot
  name="git-connections"
  alt="The Sources page's Connections tab, listing linked accounts."
/>

From the **Connections** tab, pick any available provider to be redirected there and authorize Belune. Once connected, the table shows the account login, host, and when it was connected.

<Callout type="warn">
  Deleting a connection removes that account's credentials; any application
  deploying through it will need to be pointed at a different connection.
</Callout>

## Deploy From A Connection

When creating a Git-based application, pick **Connected Account** on the repository source field, then the repository and branch. The pickers only list repositories that connection can actually see; an existing application's Settings tab shows the same fields and lets you change them.

## Push-To-Deploy

Connecting a repository registers a webhook on it automatically. A push to the application's configured branch triggers a build the same way a manual deploy does — see [Deployments](/docs/core/application/deployments) for what happens after the webhook fires, and for deploy hooks as a git-independent alternative.

## Registries

Administrators manage install-wide registry logins under **Sources → Registries**. Enter a host such as `ghcr.io`, `docker.io`, or `registry.example.com:5000`, a username, and a password or token. The password is encrypted and write-only; leaving it blank during an edit preserves the existing value.

An image application's **Settings** can hold its own registry username and password. Project members can manage that credential without administrator privileges. Pulls choose the application credential first, a matching install-wide credential second, and anonymous access last. Application settings show when an install-wide credential covers the image's registry, without exposing that login.

An application credential applies to the registry derived from its image reference. Replacing the image with another registry host requires a new password or explicit removal of the credential; an existing token is never silently sent to another host. Removing the application credential restores fallback behavior. Switching the source to git removes the image credential; running containers remain unchanged until a deploy applies the new source.

Existing `/git` links redirect to `/sources`, preserving the selected tab and connection outcome. Git provider callback URLs under `/api/git` remain unchanged.
